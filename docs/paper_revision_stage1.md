# Этап 1: воспроизводимые запуски

Математические определения и функции финансовых показателей не изменены.
`run_experiments` по умолчанию использует 4 процесса (`spawn` на macOS).
Каждый прогон сначала вызывает `random.seed(seed)` и `numpy.random.seed(seed)`;
схема seed остаётся `base_seed + run_id` (по умолчанию база 42).
Внутри сценария seeds различаются; между сценариями они общие, поэтому
сравнения сценариев по одинаковым seeds являются парными.

## Запуск и возобновление

Короткий запуск всей сетки, по одному прогону на сценарий:

```sh
python3 experiments.py --runs 1 --workers 4
```

Runner печатает абсолютный путь новой папки `tables/<UTC-время>_<id>/`.
Повторный запуск создаёт другую папку. Имеющиеся CSV и изображения не удаляются.
В папке запуска:

- `parameters.json`: все задания, seeds, число шагов, параметры шока,
  настройки сохранения, версии Python/зависимостей, хэши исходников и Git HEAD;
- `runs/0000000.csv` и далее: отдельная строка результата каждого задания;
- `runs/0000000.json`: маркер завершения с точными значениями строки и контрольными суммами;
- `runs/0000000_timeseries.csv`: все семь рядов, если указан `--save-timeseries`;
- `raw_results.csv`, `summary_results.csv`: таблицы после завершения всей сетки.

Индекс файла соответствует заданию в `parameters.json`, которое однозначно
задаёт сценарий, FX cost, run_id и seed. Размер выборки и все прежние столбцы
сводной таблицы сохранены. К отдельным результатам добавлены `seed` и `steps`.
Сводные таблицы robustness имеют прежние определения и собственные имена.
Промежуточные результаты доступны в `runs/` до завершения эксперимента.

Для продолжения повторить **те же параметры**, добавив путь:

```sh
python3 experiments.py --runs 1 --workers 4 --resume tables/<папка-запуска>
```

Число процессов можно менять. Другие параметры, исходный код и версии
зависимостей должны совпадать. Иначе runner откажется продолжать и сохранит
результаты. Завершённые прогоны проверяются по контрольным суммам и пропускаются.
Незавершённый прогон считается завершённым только после записи маркера JSON.
CSV и маркеры публикуются через временный файл и `os.replace`.
При штатном исключении блокировка `.running` снимается. После принудительного
завершения процесса ОС может остаться `.running`: перед ручным снятием этой
блокировки нужно убедиться, что прежний процесс действительно завершён.
Это блокировка записи, не файл результатов.

Python API позволяет выбрать небольшую сетку:

```python
from experiments import run_experiments

# Для workers > 1 запускать из файла с защитой __main__, как требуется spawn.
if __name__ == '__main__':
    raw, summary = run_experiments(
        [0.5], [0.4], fx_cost_values=[0.005], n_runs=3,
        workers=4, save_full_timeseries=True,
    )
    print(raw.attrs['output_dir'])
```

`rob_check.py` использует тот же runner через `run_robustness_checks`;
Python API поддерживает `workers`, `output_root`, `resume`.
Запуск robustness целиком большой: в ходе этапа 1 он не выполнялся.
`plot_results.py` при запуске создаёт новую подпапку `figures/`; импорт
больше не запускает построение графиков. Правки самих графиков отложены.

## Оптимизация и регрессия

Единственное изменение вычислений — `lru_cache(maxsize=4096)` для
`euclidean_distance` с ключом из двух кортежей координат. При новых координатах
расстояние пересчитывается; умножение на tau и порядок арифметических операций
сохранены. Случайных вызовов эта функция не содержит. Спреды и `price()`
не кэшируются, поскольку состояние рынка меняется, а `price()` имеет побочные эффекты.

Проверки запускаются короткой командой:

```sh
python3 -B -m unittest discover -s tests -v
```

Тесты сравнивают исходную формулу расстояния и кэш на 12 прогонах по 500 шагов:
все семь временных рядов, деньги и активы агентов, финансовые метрики и конечные
состояния обоих генераторов. Отдельно проверяются четыре процесса против одного,
полные ряды, возобновление после прерывания, пропуск готовых прогонов, отказ при
других параметрах/повреждённом CSV и отсутствие построения при импорте графиков.

## Замеры этапа 1

Среда: этот Mac, macOS ARM64, Python 3.12.4, 8 логических CPU.
Все измерения короткие, 500 шагов на прогон; полная сетка не запускалась.

| Проверка | До | После |
|---|---:|---:|
| Один прогон, tau=0.5, beta=0.4, FX cost=0.005, 24 seed, чередующийся порядок | 0.178256 с | 0.177011 с |
| 48 прогонов новым runner, один процесс, включая CSV/контрольные файлы | — | 8.504 с |
| 48 прогонов новым runner, четыре процесса, включая запуск процессов и сохранение | — | 7.632 с |
| 96 прогонов новым runner, четыре процесса, включая запуск процессов и сохранение | — | 11.356 с |

Кэш дал около 0.7% в чередующемся замере: это небольшой эффект, который может
быть сопоставим с шумом. Первоначальный не чередующийся замер 12 разных
сценариев дал 0.1760 → 0.1679 с, но его не следует считать надёжной оценкой ускорения.

В 96-прогонном замере первые 8 результатов появились за 4.497 с, следующие
88 сохранены за 6.584 с: установившаяся скорость около 13.37 прогонов/с.
Экстраполяция на 50 000 прогонов — около 62 минут, против около 68 минут
по первоначальному замеру четырёх процессов и 145–150 минут последовательно.
Замеры различаются методикой и нагрузкой; разницу 68 → 62 минут нельзя целиком
приписывать кэшу. Для длительного запуска разумно по-прежнему планировать
70–90 минут с учётом нагрева и дисковых расходов. Десять минут текущие
измерения не подтверждают. Сохранение всех временных рядов в этот замер
не включено и увеличит время и объём данных.

Пять регрессионных тестов проходят. Отдельное сравнение с эталоном, сохранённым
до редактирования, подтвердило точное совпадение 12 прогонов. AST функций
`build_system`, `set_all_seeds`, `compute_recovery_time_relative`,
`second_market_recovery_time`, `summarize_run`, `aggregate_results` совпадает
с исходной версией Git. Хэши исходных `tables/raw_results.csv` и
`tables/summary_results.csv` не изменились.
